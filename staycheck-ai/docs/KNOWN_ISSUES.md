## KI-001 依存パッケージの既知の脆弱性

`npm audit`(v0.3.0時点・v0.4.0でも同じ。依存パッケージは変更していない)で16件
(重大1・高8・中7)。

- **next 14.2.35**(重大): 重大の2件は「AVIF画像の最適化機能」「Windowsで動かすサーバー」が
  条件。本アプリは `next/image` を使っておらず、Railway(Linux)で動かす想定のため、
  直ちに該当する可能性は低いと見ている。ただし、Server Components・Server Actions関連の
  DoS、キャッシュ汚染などの高・中の指摘も多数ある。npmが示す修正はNext 16へのメジャー更新。
- **tailwindcss 3.x**(高、間接依存の braces / micromatch / chokidar など): 修正はTailwind 4への
  メジャー更新(開発時のみ使用)。
- **googleapis 144**(中、uuid / gaxios など): 修正は googleapis 185 へのメジャー更新。

対応方針: メジャー更新を伴うため、単独の作業として検証環境で実施する
(判定・Drive連携・ビルドの回帰確認が必要)。

## KI-002 会社・物件モードの判定でRedisを過剰に読み込む

`app/api/judge/route.ts` は、会社を選んだ判定のたびに `loadRegistrySnapshot()` で
全会社・全物件を読み込んでいる。写真1枚あたりのRedisコマンド数は
「1 + 2×会社数 + 物件数」。

- 実測(v0.3.0 E2E、会社1件・物件1件): 1枚あたり4コマンド
- 試算: 会社5社・物件20件なら1枚31コマンド、300枚で9,300コマンド
- Upstash無料枠は月50万コマンドのため、この規模では月50回程度の判定(300枚換算)で上限に達する

改善案: 選択された会社・物件だけを直接読む(2コマンド)、またはバッチ単位で
1回だけ読み込んで使い回す。判定処理の変更になるため、別作業として行う。
(標準モードはRedisへアクセスしないため影響なし)

## KI-003 Google Driveの生のエラー文が画面に表示される

`app/api/google-drive/file/[id]/route.ts` の56行目が、Google APIのエラー文を
`画像の取得に失敗しました: ${message}` としてそのまま返している。
v0.4.0の履歴には保存しない(エラーは分類コードのみ保存)が、チェック画面には表示される。
改善案: 固定の文言とコードだけを返し、詳細はサーバーログにのみ出す。

## KI-006 ビルド時の警告(Edge Runtime)

middleware.ts → auth.ts → redis.ts の経路で `@upstash/redis` を読み込んでいるため、
「Edge RuntimeでサポートされないNode.js API(process.version)」の警告が出る。
ミドルウェアはRedisを使わないため動作への影響はない。
改善案: ミドルウェアが使う署名検証部分を、Redisを読み込まない別ファイルに分ける。

## KI-007 共有パスワード方式のため会社ごとのアクセス分離ができない

ログインした人は全員同じ権限で、どの会社・物件の履歴も閲覧・削除できる。
誰が保存・削除したかも記録できない(削除時はrunIdと時刻をサーバーログに出すのみ)。
アカウント機能(ロードマップ5)の導入時に、次を追加する:

- キーの先頭に会社(テナント)の区切りを付ける(`t:{tenantId}:history:…`)
- runIdの署名にテナントを含める
- リクエストごとに、その人がその会社の履歴にアクセスしてよいかを確認する

## KI-008 保存完了前にタブを閉じた判定は履歴に残らない

保存は判定完了後に画面から送信するため、送信前・送信中にタブを閉じると、その回の
判定は履歴に残らない。v0.4では仕様として許容(承認済み)。

## KI-009 本物のUpstashでの動作確認(一部確認済み)

v0.4.0の結合テスト・E2Eは、ローカルのRedis 7をUpstash REST互換の中継で接続して実施した。
その後、利用者のPCから検証専用のUpstash DBに接続して確認した。

**確認済み(利用者による実施・報告)**

- v0.4.0の結合テスト(`npm run test:integration`、39件版)
  - 初回は期限切れ関連のテストが失敗。PCの時計がUpstashより進んでいたことが原因と判断し、
    Windowsの時刻同期後に再実行して正常終了したと報告あり(集計の数値・画面は未共有)
  - これにより、Luaスクリプト内の `TYPE` / `SET … PXAT` / `ZRANGE … BYSCORE REV LIMIT` /
    `SCAN` などが本物のUpstashで動作することを、テスト経由で間接的に確認
- 画面操作(ローカルで起動し、テスト用Upstash DBに接続)
  - 判定後の履歴保存、一覧、会社・物件・期間での絞り込み、詳細表示、削除がいずれも正常と報告あり

- 手順6(2026-10-22、利用者が実施)
  - Upstashの管理画面(Data Browser)で、写真結果キー(`history:items:…:r1`、300枚のテスト履歴)の
    TTLが「5 months 16d」であることを確認(作成から約11日後のため、作成時点で約180日だったことと整合)。
    中身はファイル名・判定・要約・チェック項目のみで、写真データ等が含まれないことをスクリーンショットで確認
  - 概要キー(`history:run:…`)のTTLと中身も確認済みと報告あり(画面は未共有)

**未確認(未完了として扱う)**

- データの自動退避(eviction)がオフであることの確認
- v0.4.1の結合テスト(41件版、時計のずれ補正・片付け処理入り)の本物のUpstashでの実行
- 「期限による実削除」テストは他の履歴が入ったDBではスキップされるため、空の検証専用DBでの実行が必要
- Railway等の本番相当の環境(HTTPS配下)での動作

## KI-010 Upstash無料枠の容量・コマンド数の上限

無料枠はデータ量250MB・月50万コマンド・1リクエスト10MB。
履歴は写真1枚あたり約0.4KB(300枚で約122KB、結合テストで実測)。
保存1回あたりのコマンド数は約8〜12(読み込み3〜4+スクリプト1+会社・物件の表示名取得)。
一覧表示ごとにインデックスの補修(最大20件)も行う。

## KI-011 アプリとRedisの時計がずれると、インデックスの期限が最大でそのずれの分だけ早まりうる

v0.4.1の結合テストで、テスト側の時計を60秒進めた状態を再現して判明した。
保存スクリプトは「インデックスの期限を延ばすか」を、アプリ側の現在時刻+インデックスの残り時間で
判定している。アプリ側の時計がRedisより Δ 進んでいると、この判定が Δ だけ甘くなり、
インデックスが最新の履歴より最大 Δ 早く期限切れになりうる。

- 影響: 保存期間180日の最後の Δ(通常は数秒以内)だけ、その履歴が一覧に出なくなる可能性がある。
  履歴データそのもの(概要・写真結果)は正しい時刻に削除され、壊れることはない
- 対応案: 期限の比較を絶対時刻(`PEXPIRETIME`)で行う。アプリ本体の変更になるため、別作業として行う
- サーバー(Railway)とUpstashはどちらも通常NTPで時刻同期されているため、本番での影響は小さい見込み

## KI-012 スマホ実機での確認には、HTTPSで公開した環境が必要

`npm start`(本番モード)ではログイン用Cookieに Secure 属性が付くため、スマホから同じWi-Fi経由で
`http://パソコンのIPアドレス:3000` に接続すると、ログインできない(Cookieが保存されない)。
パソコン上の `http://localhost:3000` はブラウザの例外扱いで問題なく使える。
スマホ実機での確認・デモは、RailwayなどHTTPSで公開した環境で行う。
v0.4.3のスマホ表示は、実ブラウザ(Chromium)のスマホ表示モードで360/390/768px幅(とPCの1280px幅)を自動検証済み。

## KI-013 360px幅で、タブ「Google Driveから追加」が省略される

チェック画面の写真の追加元タブは、360px幅では「Google Driveから…」と省略表示になる(押すことはできる)。
v0.4.3の修正範囲(メニュー・判定結果の行・選択欄/入力欄・拡大表示)の外のため、未対応として記録する。

## KI-014 ログイン失敗の回数制限は、X-Forwarded-For を変えると回避できる

ログイン失敗の制限(15分に10回)は、接続元を示すヘッダー X-Forwarded-For の先頭の値で数えている
(app/lib/auth.ts)。手元の確認(2026-10-30)では、この値を毎回変えて送ると制限がかからなかった。
公開環境で回避できるかは、Railwayの中継がこの値をどう扱うかによる(未確認)。
v0.4.3.1ではコードを変えず、デモ用パスワードを英数字20文字以上のランダムな文字列にして対応する。
コードの修正は提出後の課題とする。

## KI-015 Next.js 14 はサポート終了。画像最適化の停止後も既知の脆弱性が残る

Next.js 14 はサポート対象外で、使用中の 14.2.35 が14系の最終版のため、今後の修正は出ない。
`npm audit`(2026-10-30時点)では next に25件の指摘があり、すべてを解消するには
Next.js 15.5.28 以上への更新が必要(各APIの書き方の変更を伴うため、提出後に別作業として行う)。

v0.4.3.1 で画像最適化(/_next/image)を停止した(該当5件の入口を閉じる。停止後は404になることを確認)。
**画像最適化の停止で、すべての脆弱性が解消されるわけではない。** 残りの指摘の判断(手元での確認に基づく):

- Server Components のサービス停止攻撃(高・3件): 本アプリには Server Actions が無く(ビルド結果で確認)、
  14.2.35 は Server Actions が無いアプリでは送られた中身を解析する前に処理を打ち切る(コードと実際の送信で確認)。
  確認した範囲では届かないが、指摘の原文は「Server Actionsが無いアプリは対象外」と明記しておらず、
  未知の経路が無いとまでは言えない
- Server Actions 関連(5件)、rewrites・WebSocket・i18n・CSP nonce・beforeInteractive 関連(6件)、
  Windowsサーバー関連(1件): 該当する機能を使っていない・Linuxで動かすため、該当しない見込み
- キャッシュの汚染・取り違え(5件): 手前にキャッシュするCDNを置かないため影響は小さい見込み。
  公開環境(Railway)の中継がキャッシュしないかは未確認
- Server Actions の無いアプリに対象の送信をすると、サーバーの記録に警告が1件ずつ残る(記録量が増えるだけ)

公開デモは、公開期間の限定と定期的な監視を前提とする。今後新たに公表される指摘も、14系には修正が出ない。
